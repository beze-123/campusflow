# Team Design Decisions

These decisions are the shared plan for Engineer A and Engineer B. Both
engineers should review and agree before implementing changes that affect
shared ticket data or status values.

## Shared ticket contract

- A ticket is a dictionary containing `id`, `title`, `category`, `urgency`,
  `affected_users`, `priority`, `status`, and `assigned_to`.
- Ticket IDs are generated by the app and must be unique. Matching titles do
  not make tickets duplicates; separate reports receive separate IDs.
- Business logic accepts ticket data as function arguments so it can be tested
  without interactive input.
- Invalid ticket IDs, blank assignee names, and invalid state changes should
  raise a clear `ValueError`. The CLI displays the error and does not save a
  failed operation.

## Module responsibilities

- `ticket.py`: ticket validation, creation, and priority calculation
  (Engineer A).
- `workflow.py`: assignment, status transitions, reopening, and work-queue
  ordering (Engineer B).
- `report.py`: ticket totals and breakdowns by status and priority
  (Engineer B).
- `storage.py`: JSON loading and saving, including clear errors for malformed
  data.
- `main.py`: prompts, menu choices, calls to the business logic, and display.
- Both engineers write tests for their features and review each other's
  changes through pull requests.

## Workflow rules from the brief

- An unassigned ticket cannot move from `open` to `in_progress`.
- The normal lifecycle is `open` → `in_progress` → `resolved`.
- A resolved ticket must be explicitly reopened to `open` before it can be
  changed again.
- The work queue contains unresolved tickets, ordered by priority
  (`critical`, `high`, `medium`, `low`) and then by the numeric part of the
  ticket ID.
- Reports include all status and priority categories, including zero counts.

## Status value to confirm

The brief specifies `resolved`, while the current `ticket.py` accepts
`closed`. Engineer A and Engineer B should agree to use `resolved` throughout
the app and stored data before integrating workflow changes.
